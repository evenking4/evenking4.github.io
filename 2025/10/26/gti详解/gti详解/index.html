Git详解

简介

Git 是一个快速、可扩展的分布式版本控制系统，它拥有异常丰富的命令集，可以提供高级操作和对内部的完全访问。[2]

快速上手

CheatSheet [1]

初始化

创建一个文件夹作为git的项目目录

mkdir -p ~/git-demo && cd ~/git-demo

初始化git仓库

git init

可以看到，这条命令在当前目录下创建了一个.git文件夹。该文件夹记录了当前仓库的所有信息（在TODO一节中会详细解释）。

第一次提交

创建一个文件，并编辑一点内容

echo '11111' > 1.txt

使用git status查看 git 仓库的状态：

可以看到，目前1.txt是处于未跟踪的状态。使用git add 1.txt将他加入暂存区：

修改1.txt文件的内容，再次git status可以看到1.txt的修改记录被移到了工作区（标红的部分）。

输入git commit -am "First Commit"将代码提交到代码仓库。git commit原本只会提交暂存区的内容，-a参数可以自动将工作区的所有内容提交到暂存区再commit。-m参数后跟一个字符串表示提交信息。

工作区、暂存区(stage)与代码仓库

在一个git项目中，一个数据对象（这里可以先理解成一个文件）可以有四种状态：未跟踪、在工作区、在暂存区、在代码仓库（这里不考虑贮藏区），如下图所示：

当一个文件被创建时，他首先会处于未被跟踪的状态。使用git add <file>可以将他加入暂存区，暂存区中保存所有新增文件、删除文件、修改文件的记录，使用git commit可以生成一个snapshot，将暂存区中的所有修改提交至代码仓库，形成一次提交。当修改已保存在代码仓库或暂存区的文件时，该文件会被转移至工作区，工作区保存所有内容发生过修改的文件。使用git checkout -- <file>可以丢弃工作区所有的修改，使用git add <file>可以将工作区的文件的修改保存至暂存区。而git reset可以将当前暂存区所有已保存的修改移回原有的状态，即工作区或未跟踪。（这里只是改变文件的状态，并不会把修改的内容撤回）

最佳的一个提交内的工作回滚实践：

如果你只想撤销工作区内某个文件的修改：git checkout -- <file>，同时，git checkout -- .可以撤销工作区内所有文件的修改。

如果你想撤销整个暂存区和工作区内的修改，可以使用git reset --hard 撤回。

版本更新与代码回滚

你的每一次git commit都会形成一个提交记录，也就是一个版本。可以使用git log查看历史提交记录。

git保存了你每个版本中的所有代码，可以使用git reset 在不同版本之间切换。其有三种提交模式，下表列出了三种模式的不同区别：

模式 提交 暂存区 工作区
–soft 回退 保留 保留
–mixed（默认） 回退 清空 保留
–hard 回退 清空 清空

这里做一个实验来测试这三者的区别，可以看到我上面git log的结果显示我有三次提交，每次第二第三次提交都分别增加了一个2.txt和3.txt。此时的提交树如图所示：

输入git reset --soft HEAD~2（这里的HEAD~2，表示HEAD的父结点的父结点，即寻找父结点两次）。输入git status查看代码仓库状态：

可以看到此时前两次提交的修改都被移到了暂存区中，同时前两次提交记录也没有了。

Tips：虽然git log中无法看到提交记录，但其实那两次commit依然存在，如果你能记得那两次提交的哈希值依然可以移动到那两次提交的版本

重置刚刚的环境，输入git reset --mixed HEAD~2

可以看到修改依然保存，只不过是放在了工作区或未跟踪（因为这里我都是新增文件，所以回滚后都是未跟踪状态，如果是修改文件则会在工作区）。

重置环境，输入git reset --hard HEAD~2

可以看到这次回滚不仅回滚了代码仓库的内容，并且还将版本之间的修改完全丢弃了。

由此可以看出，之前我们用于丢弃工作区和暂存区的命令git reset --hard HEAD其本质是回滚到本次提交最开始的状态并丢弃工作区和暂存区的所有修改。

刚刚我们使用的git reset <model> <id>中都的commit_id都是用相对引用的方式，如HEAD~2就是找HEAD指向的节点的父结点的父结点。我们还可以直接输入每个commit节点的id来移动到对应的commit节点。commit节点的id就是其哈希值，可以在git log中看到，我们不需要把哈希值全部输完，只要输入前4位且没有发生哈希碰撞，git就会自动帮我们匹配对应的节点。

我们刚刚提到，被回退的提交节点虽然不会再出现在提交记录中了，但是我们依然可以用git reset <id>来找到。从之前的git log结果中可以看到第三次提交的节点的哈希值是040c…，这里我们输入git reset --hard 040c

可以看到，不仅移到了之前被回退的节点，删除的文件也返回了。

分支与合并

在git中，当你想要开发某个功能，或者基于某个现有的版本做一些新的尝试时，可以使用branch来开辟一条新的分支。

顾名思义，branch就是在原有的提交树上开辟一条新的分叉，你可以在上面进行一些一些代码的修改提交而不影响原来的分支。git代码仓库初始会有一条main分支，我们可以用git branch（使用了默认的–list参数）来查看所有分支，使用git branch <name>来创建一个新的分支，使用git switch <name>来切换到另一个分支，下图展示了创建一个分支，并切换到其上的过程：

此时，我们在dev分支下创建一个新文件2.txt并提交，再切换到main分支上，可以看到刚刚创建2.txt不见了。

我们再在main分支下创建新文件3.txt并提交，此时可以看到两个分支各持有2.txt和3.txt，并且git log的输出结果也只有在本分支下的提交记录。

当一个功能开发测试完毕想要合并到主分支上时，就需要使用到git merge来合并分支，合并分支时情况可能会遇到多种不同的情况，并采取不同的合并策略：

  • Fast-forwar merge（快进合并）

    这是最简单的一种合并情况，当一个分支是另一分支的祖先时，只需将落后的分支指向较新的分支即可完成合并，举个例子

  • 3-way merge

    当两个分支都拥有共同祖先但又都有各自新的代码提交时，就需要git产生一个新的合并提交，举个例子：

    图中feature和master都有共同的祖先节点B，但又各自又都有新的代码提交。此时若用git merge合并，git会首先找到他们共同的祖先节点B，然后对比B→C和B→E的提交，最终生成一个新的合并提交F。

  • Conflict merge（冲突合并）

    当两个分支同时修改了同一文件的同一部分内容时，就会发生合并冲突。Git将会停止合并，并交由人工判断解决冲突。

    这里我们分别在main分支和dev分支中修改1.txt的第一行内容，提交后进行合并发生合并冲突。

    此时有两种选择，一是使用git merge --abort来撤销本次合并，二是修改发生冲突的文件，手动指定保存哪个版本的内容并再次提交，这里我们修改1.txt并选择保存main分支的版本并再次提交。

    Tips：还存在一种合并分支的命令git rebase，其可以将两条不同路径上的提交整理到一条路径上从而减少过多的提交节点，使得整体提交树变得更整洁。我们这里不做过多讨论。

远程分支

新建一个代码仓库，并进行一次提交

在github中新建一个仓库

在本地创建一个远程分支

git remote add origin <url>

这里的origin，可以理解为给远程仓库取了个别名。查看.git/config的内容

这里可以看到，config中已为远程仓库origin建立了映射关系，但实际上并未真正推送远程分支。

使用命令git push -u origin main将本地分支main推送至远程仓库origin，此时刷新github 代码仓库的页面可以看到仓库中已有1.txt。

输入git branch -a可以看到，此时本地仓库也多了一条远程分支origin/main

对于本地仓库中的远程分支，其所代表的上一次与对应远程仓库同步（可能是推送也可能是拉取）时远程仓库对应分支的提交状态，并且远程分支是一个只读分支，我们无法切换到远程分支上进行提交等操作。

我们在本地仓库中创建一个文件2.txt并提交，在github的远程仓库页面中创建一个文件3.txt。然后在本地仓库使用git fecth origin同步远程仓库的分支git 。此时远程分支同步了远程仓库新建3.txt的更新，而本地分支main则提交了新增2.txt的更新。

输入命令git log --graph --oneline --decorate --all可以查看以图的形式查看提交记录：

可以看到，两个分支各进行了一次提交。我们输入git merge origin/main合并提交，此时，本地仓库中存在1.txt、2.txt、3.txt三个文件。

Tips：git pull命令也可以拉取远程仓库的更新，其等价于git fetch+git merge。

我们还可以将本地的修改推送至远程仓库，输入命令git push -u origin main，可以看到，远程仓库也多出了2.txt这一文件。

但当推送本地分支时，要求当前分支完全超越远程仓库中的分支，即远程仓库中的对应分支的提交，本地要提交的分支必须都有。换句话说，远程分支要同步成本地分支只能使用fast-forwars合并的方式。

这里我们在本地仓库创建文件4.txt并提交，在github远程仓库创建一个文件5.txt。此时，我们输入git push -u origin main进行提交会被远程分支拒绝

我们使用git pull同步远程仓库后再次推送即可同步成功。

tag

标签（tag）是git中一个非常实用的功能。对于某些比较重要的提交（例如一次大的版本更新），我们可以用git tag <tag_name> <commit_id>来为一次提交打标签，若未指定commit_id则会默认为当前所在的提交打上标签。

输入git tag v1.0为当前提交打标签，然后还可以用git tag查看所有标签

进行一次新的提交对后，我们可以用git checkout <tag_name>来进入游离HEAD状态（detached HEAD），强制移动到某次特定提交上。

git config

git的配置信息非常重要，其影响了git中许多的操作和提交时的一些附录信息。

git的配置信息有三个层级：system（系统级）、global（用户级）、local（仓库级）。优先级为：local > global > system，影响范围则相反。

system级的配置文件存储在/etc/gitconfig中，global级的配置文件存储在~/.gitconfig中，local级的配置文件存储在.git/config中。

可以看到，git的config文件内部是一种INI-like格式（类似于INI文件）

我们可以使用类似于git config core.bare或git config branch.main.remote的形式来读取配置信息，常用命令如下

  • 增

    git config [<scope>] <key> <value>

  • 删

    git config [<scope>] --unset <key>

  • 改

    git config [<scope>] <key> <value>

  • 查

    git config [<scope>] <key>

    git config --list（查看当前应用的配置信息）

其中的[<scope>]可以是–local、–global和–system，默认是–local。

git config中常用的配置信息如下：

  • user.name与user.email：记录了当前使用作者的一些信息，会附加到每次的提交信息中，使得整个多人合作的项目可以溯源开发者。
  • http.proxy与https.proxy：对于某些github上的代码仓库可能需要配置代理服务器才能访问，这里配置了http与https的代理服务器url。
  • …

从.git看Git原理

我在刚接触git时就很好奇，git是如何存储不同版本的所有代码的。如果只是把每个版本的所有的代码文件打个压缩包存起来，那得占多大空间。而且这也不利于各个版本之间复杂的比较与合并操作。

学习理解git的底层原理，可以有助于加深对各种命令的记忆和理解。如果能像庖丁解牛一样看到一条命令就能大致知道他大致做了什么操作，大致有哪些存储的数据结构能支持他实现某些特性，那想必这本身就是一件很爽的事情。

git对象标识符

git中主要有以下这几种对象（object）：

  • blob

    blob（binary large object），用于存储文件内容的数据结构，其只保存文件的内容，不包含文件的文件名等信息，相同内容的文件会指向同一个blob。

  • tree

    tree约等于文件夹，其存储当前目录中所有{文件名/目录ming→blob对象/tree对象}的信息，以及文件与目录的权限信息。

  • commit

    commit表示一次提交。

我们先创建一个文件1.txt并将其加入暂存区

此时可以看到.git/objects中多出了一个类似于哈希值的文件

这个e69de…的文件就是1.txt文件对应的blob对象。git中默认使用SHA-1算法来计算哈希值，对于一个文件要计算其blob对象的哈希值，计算方法公式是SHA1(blob <文件长度>\0<文件内容>)。

可以看到1.txt和2.txt虽然文件名不同，但是因为文件内容相同，所以都指向同一个blob对象。由此可见，一个commit就是通过这样索引的方式来保存整个当前版本的代码，又因为其保存了父节点的哈希值，所以可以实现版本控制与代码回滚。

最后总结一下

  • 一个文件对应一个blob对象，文件内容相同的文件都指向同一个blob对象，无论文件名是否相同。
  • 一个目录会对应一个tree对象，tree对象中的保存了许多目录项，一个目录项可代表一个blob对象或tree对象，一个目录项包含了该对象的访问权限、类型、哈希值、名称信息。存在一个隐式的tree对象作为整个项目的根目录。
  • 一次提交对应一个commit对象，commit对象中包含了本次提交的注解、作者、提交者的信息。每一个commit对应一个作为根目录的tree对象。除了第一个commit，所有commit还会记录其父结点的哈希值，如果是个合并提交，则会包含所有父结点的哈希值。

HEAD与refs

git项目中永远存在一个头指针HEAD指向当前所处在的提交（不考虑第一次提交前）。查看.git/HEAD中的内容可以看到其保存了当前所在分支的路径。

refs文件夹中主要有三个文件夹：heads（存储了所有本地分支）、remotes（存储了所有远程分支）、tags（存储了所有标签）。查看这些文件所保存的内容：

可以看到他们只是简单保存了指向节点的哈希值。所以在git中创建一个分支的成本非常小，他不会像SVN那样每个分支都会创建一个chunk来保存大量代码，他只是创建了一个指针指向当前提交，并且这个指针会随着每次提交而不断移动。

值得一提的是，HEAD可以处于一种特殊的分离模式，当强制将HEAD移到某个没有任何分支指向的节点时，HEAD就会处于游离状态。

这里我用git checkout <commit_id>将HEAD移到之前的节点，然后查看.git/HEAD：

可以看到此时HEAD中不在指向refs中的某个分支，而是直接存储对应节点的id。

游离HEAD状态下也可以进行代码的修改和提交，但这本身是一种很危险的状态，后续如果找不到对应的commit_id将无法返回，并且因为没有绑定branch和tag，也可能会被git的垃圾回收机制清除。
